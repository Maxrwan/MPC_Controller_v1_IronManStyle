## Scenario 1 — execute an approved simulation

**Task:** choose `VDL1_BASE`, inspect its actual fixed parameter/initial-state/input/source snapshot,
add an optional engineering note, launch via the existing worker, then reopen it after leaving the view.

**Pass:** the normal nominal-only request and owned lease/resource controls are used; the preserved
0.500 s / 0.005 s / onset-tick-20 contract yields the genuine retained output or an explicit retained
failure. For a successful software smoke: 101 state rows / 100 applied controls, immutable manifests,
actual XY/diagnostics and independent outcome/evidence/coverage statuses. Completion alone is not a
qualification label; application of Q still requires its exact production applicability checks.
Unsupported NMPC/tire/arbitrary-parameter options are unavailable rather than silently substituted.

**Minimum verification:** one bounded nominal functional smoke, request/worker/readback and UI data
assertions; use existing canonical parity checks, not a new golden trajectory generated by the adapter.
Retain both V0.1 entry-point/worker parity checks. No all-case/grid campaign. This scenario establishes
execution mechanics, not physical validity or a tracking-performance claim.

## Scenario 2 — compare retained experiments

**Task:** reopen the existing Q BASE/IZ pair directly from its archive source, overlay actual r/vy,
steering and available diagnostics, and inspect the reported qualification/metric difference.

**Pass:** source/units/profile/time/geometry and original outcome/evidence are visible. Without selected
Q the pair is a controlled candidate; with valid Q it is a qualified synthetic comparison. The retained
peak yaw separation is `0.008904428222327412 rad/s`; the UI reads it from Q rather than inventing a
new metric. Raw times are preserved. With BASE/IZ/CF selected, the two BASE edges qualify, IZ↔CF is
illustrative, and there is no blanket “three-run controlled” label. Bad/missing required evidence is
invalid; no interpolation, automatic time shift or physical normalization hides differences.

**Minimum verification:** existing actual-Q read-only reader test plus two-/three-run UI traces and
pairwise labels. Use a disposable corrupt copy for rejection, never mutate/reseal accepted artifacts.
Metrics with different windows/profiles may be displayed descriptively but cannot receive a causal rank.

## Scenario 3 — investigate a controller-availability failure

**Task:** open C0 `original155.json` under its explicit synthetic software profile, inspect available
states/controls, plans/packets, reserve, missed handoffs and fallback on one chronology.

**Pass:** identify recorded misses at 0.170 and 0.330 s, late discard/readiness, and
`trajectory_exhausted` fallback at 0.400 s. A missing acceptance/first-TVLQR-use time stays null, not
zero. Failed availability does not become an accepted late trajectory or proof that IPOPT failed.
Use actual native sample counts/timestamps, not the lab's unrelated N+1 convention. A missing reference
or coordinate channel is unavailable; no fabricated route/command or continuous-time Safety claim.

As a separate incomplete-output example, the preliminary serialization archive must expose its actual
TypeError and absent summary. A saved `Solve_Succeeded` row does not make its exporter successful or
establish a solver-failure explanation. Keep it unqualified and label its legacy evidence limitations.

**Minimum verification:** source-bound fixture parser/event mapping and literal chronology/UI checks;
no planner execution, fallback retuning or failure reconstruction. This is an approved synthetic
control-system failure fixture, not a claim of a real-vehicle or optimizer convergence failure.

## Scenario 4 — replay recorded telemetry

**Task:** open/import a versioned software evidence package for existing BASE nominal; play/pause,
seek to onset and terminal samples, and inspect synchronized states/controls/stored XY and actual events.

**Pass:** panes use the same selected state cursor and identify the actual timestamp/source of each
retained channel sample. At 0.100 s the recorded command changes while the state remains the actual
onset sample; at 0.500 s terminal held input is informational, referring to the last actual applied
control, with no new row or interval. No dynamics or fresh XY conversion is run for playback. Optional absent solver/
event channels say unavailable. A missing required sample/file in this fixed-grid profile quarantines
the record; it is not interpolated into a complete trajectory. A genuine partial retains its real end.
Other future gapped profiles need declared gap semantics; no universal hold/fill rule is assumed.

**Minimum verification:** deterministic viewer-state/seek tests, actual bundle hash/schema readback,
cross-pane sample identity and disposable missing-data fixtures. Label generated playback fixtures
synthetic. No Raspberry Pi, physical telemetry or hardware test is implied.

## Scenario 5 — prepare an engineering demonstration

**Task:** reopen existing BASE and STEER_HIGH from Q, inspect trajectory and synchronized engineering
signals, compare outcomes and export a clear figure/standalone HTML or evidence package.

**Pass:** exported content has readable SI axes, run/reference/source identities, selected window,
classification and permanent synthetic/model limitations. Source data/manifest bytes remain unchanged;
presentation settings and annotations are separate. An evidence ZIP discloses any unverified logs;
it is not relabeled a wholly certified package. The export can be reopened locally; a claimed image
format must actually work. No scientific record is rewritten and no demo trajectory is newly generated.

**Minimum verification:** export/reopen, content/hash/units/labels assertions and visual inspection of
one actual exported figure if a figure format is delivered. Reuse accepted data and the launcher.
Do not introduce a large report framework, new frontend engine or elaborate vehicle animation.

Passing all five scenarios after the relevant stages, independent Engineering Review and applicable
exact-revision Verification is the proposed MVP acceptance gate. No scenario authorizes physical
integration or a new scientific assumption; the [decision list](DECISIONS_AND_NEXT_TASK.md) controls those.
